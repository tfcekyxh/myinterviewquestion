## 部署前评估（用户问「还需要做什么，能直接部署吗」）

结论：**架构上没有硬阻塞**（Express + SQLite 单端口正是发布沙箱支持的形态，
沙箱不支持 MySQL/PG/Redis，我们一个都没用）。但部署前有三件事必须先处理：

1. **环境变量是最大卡点**：`.env` 不在 git 里，上传时大概率不会带上 →
   线上没有 `APP_ACCOUNT` / `APP_PASSWORD` / `SESSION_SECRET`，
   `ensureUser()` 会报错、`process.exit(1)`，服务根本起不来。
   方案：用 `startCmd` 注入这三个变量。
   ⚠️ `SESSION_SECRET` 尤其不能省 —— 不设就用固定的 `dev-only-insecure-secret`，
   公网环境下别人能伪造 session cookie。
2. **前端产物**：`dist/` 在 `.gitignore`，沙箱只 install + start，不一定跑 build →
   `startCmd` 必须带上 `npm run build`，否则首页就是 503「前端尚未构建」。
3. **数据是空的**：线上是全新库，要靠刚做的整库还原（传 .db）或重新导入 PDF。

部署的额外收益：公网 HTTPS → 手机**不用再装自签证书、不用和电脑同一个 Wi-Fi**，
录音随时可用（Safari 只在安全上下文给麦克风权限）。

顺带能验掉最后一个风险点：重新发布一次，看 SQLite 数据还在不在。

## 改动

`server/db.js`：数据库打不开时抛出可读的错误，**不静默退到临时目录**。
部署环境未必保证磁盘可写，静默 fallback 到 tmpdir 会让服务起来、数据却随时消失，
用户还以为存住了 —— 宁可起不来，把原因暴露在日志里。

`scripts/set-password.mjs`（新）：改 .env 里的 APP_PASSWORD **不会生效**（ensureUser 只在用户
不存在时写库），换密码必须改 users 表。线上改法：GET /api/backup 下载 → 本地改 →
POST /api/restore 传回去。脚本会顺手清掉旧 session。

### 踩到的两个真坑（下次重发前必看）

1. **`data/` 会被一起上传**（工具只排除 node_modules/.git/构建产物）。
   所以本地 `data/app.db` 覆盖了线上库，导致：
   - 注入的新密码**没生效**（users 表里已有 admin，ensureUser 直接 return）—— 症状是新密码登录 401
   - 但题库和进度倒是跟着上去了（200 题 + 背到第 13 题 + 7 条复习记录）
   → **每次重新发布会用本地库覆盖线上数据**。要保持两边一致，就得让本地库也是最终想要的状态。
2. 改密码走了「下载线上库 → 本地 scripts/set-password.mjs 改 → 还原回去」，一次成功。
